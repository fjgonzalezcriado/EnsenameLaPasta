# HV-057: Segundo proveedor de noticias — RSS de onvista.de

## Información General
- **Código**: HV-057
- **Fecha inicio**: 2026-11-02
- **Estado**: 🟡 En progreso
- **Prioridad**: 🟡 Baja (ampliación de HV-055, no crítica)
- **Tipo**: Evolutivo
- **Depende de**: HV-055 (`INewsProvider`/`YahooNewsProvider`) — mismo contrato y patrón de degradación

## Contexto
El usuario sigue HY9H.F (SK Hynix GDR, Frankfurt) y preguntó si se podían incluir también las noticias de onvista.de, un portal financiero alemán, como complemento a las de Yahoo (HV-055). Investigación previa a este evolutivo:

- onvista.de **no tiene API pública documentada**.
- Sí expone **feeds RSS 2.0 reales y filtrables por instrumento**, verificados en vivo:
  ```
  https://www.onvista.de/news/feed/rss.xml?entityType={STOCK|INDEX}&entityValue={id}
  ```
  - `entityType=INDEX&entityValue=20735` → DAX (confirmado: titulares específicos del DAX, no genéricos).
  - `entityType=STOCK&entityValue=12952618` → SK Hynix (GDR) / HY9H.F (confirmado: titulares específicos sobre SK Hynix).
- Formato RSS estándar: `<title>`, `<link>`, `<description>` (a veces vacío), `<pubDate>` en RFC822 (ej. `Wed, 28 Oct 2026 15:50:46 +0100`), `<guid>`, `<dc:creator>`.
- **Limitación clave**: `entityValue` es un ID interno propietario de onvista que **no se puede resolver desde el ticker/símbolo**. Hay que localizarlo manualmente navegando a la página del instrumento en onvista.de (aparece en la URL del enlace "RSS-Feed auf ... abonnieren" de esa página) y guardarlo en un mapeo `Symbol → (entityType, entityValue)`.
- Las noticias llegan **en alemán** (a diferencia de Yahoo, que en HV-055 salía mayoritariamente en inglés).

## Objetivo
Añadir onvista.de como fuente de noticias adicional, reutilizando el contrato `INewsProvider`/`SymbolNews` de HV-055, para símbolos que el usuario mapee explícitamente (empezando por HY9H.F).

## Especificaciones Técnicas

### Backend
- `OnvistaNewsProvider` (clase propia, no implementa `INewsProvider` directamente — ver `IOnvistaNewsProvider` más abajo) en `Infrastructure/News/`.
- Descarga el XML con `HttpClient` (nuevo cliente `"Onvista"` registrado en DI, mismo patrón que `YahooNewsProvider`), parsea con `XDocument` los campos `title`/`link`/`description`/`pubDate` (RFC822 → `DateTime` UTC) → mapea a `NewsItem`.
- Degrada honesto igual que `YahooNewsProvider`: sin mapeo para el símbolo, HTTP no-2xx, XML inválido o feed vacío → devuelve lista vacía (sin lanzar). No necesita su propio mensaje de "sin cobertura" porque el combinado (ver abajo) ya lo resuelve a nivel agregado.
- Mapeo `Symbol → (entityType, entityValue)`: vive en configuración (`appsettings.json`, sección `Onvista:SymbolMap`), mismo patrón que `TwelveDataOptions`/`AlphaVantageOptions` ya existentes. Sin migración; añadir un símbolo nuevo es editar config y reiniciar.
  - Semilla inicial: `HY9H.F → (STOCK, 12952618)`.

### Combinación de fuentes (lista única mezclada por fecha)
- `NewsItem` gana un campo `Source` (`"Yahoo"` | `"onvista"`) para poder distinguir el origen visualmente en la lista combinada (badge/icono junto a la fecha).
- Nuevo `INewsAggregatorService.GetNewsAsync(symbol, max)`: llama a `YahooNewsProvider` y `OnvistaNewsProvider` en paralelo, concatena sus `Items`, ordena por `PublishedAtUtc` descendente y recorta a `max`. `HasNews=true` si al menos una fuente aportó algo; `Message` ("Sin noticias para este símbolo.") solo si **ambas** quedaron vacías — así D3 queda resuelto de forma natural: un símbolo sin mapeo onvista simplemente no aporta items al combinado, sin necesidad de un mensaje de degradación por fuente.
- `NewsController` pasa a usar `INewsAggregatorService` en vez de `INewsProvider` directamente (o `INewsAggregatorService` implementa `INewsProvider` para no tocar el controller — valorar al implementar).

### Frontend
- Reutiliza el mismo switch "📰 Noticias" de HV-055 (sin añadir un segundo switch): ahora pinta la lista combinada. Cada item muestra un badge pequeño con la fuente (p. ej. "Yahoo" en azul / "onvista" en gris) junto a editorial+fecha.

### Sin cambios en Domain/BD (no hay persistencia de noticias, igual que HV-055; no confundir con `NewsSentiment` de HV-056, que es un agregado distinto).

## Decisiones de diseño (resueltas con el usuario el 2026-11-02)
- [x] **D1 — Combinación de fuentes**: lista única mezclada por fecha (`PublishedAtUtc` desc), con badge de origen por item.
- [x] **D2 — Dónde vive el mapeo `Symbol→entityValue`**: `appsettings.json` (`Onvista:SymbolMap`).
- [x] **D3 — Símbolos sin mapeo onvista**: degradan silenciosamente (onvista no aporta items al combinado); el mensaje de "sin noticias" solo aparece si ninguna de las dos fuentes tiene nada.

## Notas de Implementación
- El RFC822 de onvista (`+0100`/`+0200` según DST) se parsea bien con `DateTimeOffset.TryParse` nativo de .NET — no requiere parser manual. Verificado: "Wed, 28 Oct 2026 15:50:46 +0100" → `2026-10-28T14:50:46Z`.
- `NewsItem.Source` con default `"Yahoo"` evitó tocar `NewsSentimentServiceTests.cs` (HV-056), que construye `NewsItem` sin ese parámetro — cambio mínimo, sin tocar código de otro evolutivo.
- Smoke test real reveló algo útil más allá de la validación técnica: **para HY9H.F, Yahoo ahora mismo no devuelve ninguna noticia** (cobertura pobre de small/mid caps europeos, ya documentado en HV-055) — la lista combinada son las 15 de onvista. Para AAPL, Yahoo sí aporta 5 noticias reales (`source: "Yahoo"`). Esto confirma el valor real del evolutivo: onvista cubre huecos de Yahoo, no es redundante.
- `OnvistaNewsProvider`/`NewsAggregatorService` degradan sin lanzar en todos los casos cubiertos por tests (sin mapeo, HTTP 500, XML malformado, feed vacío, ambas fuentes vacías).
